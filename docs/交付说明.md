## 三、黄果现在的真实状态（本次实测，结论与上一版说明相反）

上一版说明里写「黄果整体下线」——**那个结论是错的，现在已经推翻。**

我今天把官方 App（2.1.2 版，Flutter）的 APK 拉下来，从 `lib/arm64-v8a/libapp.so`
里提取出真实域名池，逐个实测，结果：

| 检查项 | 实测结果 |
| --- | --- |
| 官方内容站 | **`https://huangguoai.io` 活着**，接口返回明文 JSON |
| 官方 App 后端 | `api1.aicctv.net`、`bak.wouogiuqi.cc` 均返回 200 |
| 备用域名池 | `api1~6.ncsgampn.cc` 目前连不上（DNS/回源均失败） |
| `w2.sukzhuxxq.cc`（旧跳板指向） | NXDOMAIN，已废弃 |
| 社区 Workers 反代 | 域名被污染到 Facebook IP 段（`31.13.x.x` / `69.63.x.x`），国内不可达 |

**为什么你的网络可能打不开**：`huangguoai.io` 在这台机器上的系统 DNS 会解析到
`106.74.25.198`（运营商拦截页），而 DoH 查到的真实 IP 是
`43.230.144.240` / `103.49.212.243` 等。这属于 DNS 污染，不是站点挂了。
手机换用移动数据、或换个 DNS，通常就能正常解析。

## 四、插件能做什么、不能做什么（请务必看这一节）

### 能：浏览全部内容

- 首页（最新短剧 + 热播榜两个区块）
- 分类：AI短剧 / AI漫剧 / 换脸专区 / 魔改专区
- 榜单：热播榜 / 推荐榜 / 潜力榜
- 吃瓜：全部 / 热门 / 原创
- 专题（动态拉取）
- 搜索
- 作品详情 + 分集列表
- 封面（图床密文，插件内解密后交给宿主；**v4 曾误判为明文直链，导致封面全部加载失败，v4.1 已修**）

### 能：匿名播放（v3 的「不能播」结论已被推翻）

v3 判定「播放与登录态绑定」，**这个结论是错的**，错在端点用错，不是权限问题：

| | 端点 | 匿名结果 |
| --- | --- | --- |
| ✗ | `GET /api/videos/{id}/play?ep=N` | 200，但 `video_url` 全空（只有时长、标题） |
| ✓ | `POST /api/videos/{id}/episodes/{ep}/playback` | 200，返回真实 m3u8 |

正确端点必须走 `dx150-edge-v1` 的 **playback** 作用域。实测返回：

```json
{"data":{"streams":{"main":"https://yd-lphu-hls.tjyyjk.cn/videos5/…/xxx.m3u8?auth_key=…&via=dx150&via_bm=dx"}}}
```

这条 m3u8 拉下来是 **38 个分片 / 208 秒**的完整正片（作品时长字段 207 秒），
分片 AES-128 加密由播放器原生处理，不是试看片段。作品 12 与 117 均验证通过。

**所以不需要账号、不需要 Cookie。** 插件 v4.1 的播放链路：

1. 先走 dx 加密通道 `POST /api/videos/{id}/episodes/{ep}/playback`；
2. 失败再退回明文 `/api/videos/{id}/play?ep=N`；
3. 两路都空才报错，并说明是「该集没片源」还是「需要 Cookie」。

`cookie` 与 `cookieAuth` 两个设置项保留，但只是兜底，**平时留空即可**。

### 关于「帮我填 Cookie」

填不填都不影响播放了。如果哪天真需要填，获取方式是这样（我无法代填的原因也在这里）：

1. 电脑 Chrome 打开 `https://huangguoai.io` 并登录（需要你手机收验证码）；
2. F12 → Network → 点任意一条 `/api/` 请求 → Request Headers 里的 `Cookie:`；
3. 把 `Cookie:` 后面**整段**复制，粘贴到插件设置的「账号 Cookie」。

我不能替你完成这一步，是因为登录必须用你的手机号和短信验证码，我这边没有你的账号。
如果你把 Cookie 字符串发给我，我可以直接帮你验证它能否取到播放地址。

## 六、这台机器以后怎么重新打包

之前 Android 构建一直失败，根因是**中文路径被 GNU binutils 按 GBK 误解码**，
以及**内存不足导致 rustc 被系统杀掉**。现在都已解决，全部固化在 `E:\HGhub-v005\env.sh` 里。

重新打包只需：

```bash
source /e/HGhub-v005/env.sh
cd /e/HGhub-v005/HGhub-0.0.5
pnpm tauri android build --debug --target aarch64 --apk --ci
```

产物在：
`src-tauri/gen/android/app/build/outputs/apk/universal/debug/app-universal-debug.apk`

### env.sh 里每一项的作用（改动前请先读）

| 变量 | 为什么必须有 |
| --- | --- |
| `RUSTUP_HOME=E:/rustup` | `C:\Users\雷志程\` 会被 ld 读成 `C:\Users\À×Ö¾³Ì\`，报「rlib 不存在」 |
| `CARGO_HOME=E:/cargo` | 同理，`ar` 会把 registry 里的 `.o` 路径读错 |
| `TMP/TEMP=E:/tmp` | 同理，`dlltool` 无法在中文临时目录建文件 |
| `PATH` 前置 mingw | `ring`/`getrandom` 的 build script 需要 `gcc.exe` |
| `…-clang.exe`（不是 `.cmd`） | rustc 无法 spawn `.cmd`；把 `clang.exe` 复制成带 triple 的名字，clang 会从文件名推断目标 |
| `RUSTC=<绝对路径>` | 本机有两个 rustup home，不固定会混用，报 `metadata stub for rlib core` |
| `CARGO_TARGET_AARCH64_LINUX_ANDROID_RUSTFLAGS` | 与 Tauri 内部构建保持同一组参数，否则 Gradle 侧会全量重编 |
| `CARGO_BUILD_JOBS=4`、`PROFILE_DEV_DEBUG=0` | 16G 内存下防止 rustc 被杀 |

另外两个坑，遇到时直接照做：

1. **`explorer.exe` 内存泄漏**：实测它能占到 8.3 GB，导致只剩 0.9 GB 可用，
   于是 rustc 崩溃并报 `0xc0000409 STATUS_STACK_BUFFER_OVERRUN` 或
   `os error 1453 配额不足`。这两个看似无关的错误其实是内存不足。
   处理：`Stop-Process -Name explorer -Force`，之后可用内存会回到 8.8 GB。
2. **Gradle 发行包**：`gradle-8.14.3` 已经解压在
   `E:\HGhub-build\gradle-home\wrapper\dists\` 下，不用再下载 130 MB。

## 八、插件 v4.1 的自测情况

### 加密通道（`E:\HGhub-v005\test_plugin_v4.mjs`，连真实站点）

9 项断言全部通过：

- 作品 12 第 1 集 → 取到 m3u8，2 个流（主源 + HEVC）
- 作品 117 第 1 集 → 取到另一条 m3u8，验证不是写死的单条地址
- m3u8 实际下载 → HTTP 200、`#EXTM3U` 开头、38 个分片、含 `METHOD=AES-128` 密钥行
- 会话复用：两次播放只握手一次（宿主 fetch 共 4 次）

这条测试最有说服力的地方是：**宿主桩里的 AES-GCM 就是标准实现，
只要手写 P-256 有任何一个字节算错，握手就解不出明文。** 能一路拿到分片，
说明 ECDH → HKDF → AES-GCM 三段全对。

### 封面解密（`E:\HGhub-v005\test_cover_v41.mjs`，15 项断言，连真实图床）

v4 的封面全坏，原因是我把图床当成了明文源。实测证据链：

| 检查项 | 实测值 |
| --- | --- |
| 封面 URL | `https://pic.qnlycc.cn/upload_01/.../xxx.jpg?auth_key=...` |
| HTTP 状态 | 200，`Content-Type: binary/octet-stream` |
| 字节数 | 174816，**正好是 16 的倍数** |
| 前 12 字节 | `093de3b1fc4af46ff223ac4c`，不是 `ffd8ff` |
| 香农熵 | **7.999 bits/byte**（8 = 完全随机） |
| 两张不同封面 | **前 640 字节完全相同**，第 640 字节才开始不同 |

密钥不在别处，就写在站点自己的
`/static/web/js/plugins/crypto-image-protocol.js` 里：

```js
window.CryptoImageProtocol = Object.freeze({
  decryptEnabled: true,
  decryptKey: "f5d965df75336270",
  decryptIV:  "97b60394abc2fbe1"
})
```

用这对密钥按 AES-128-CBC / PKCS7 解密，前 16 字节变成
`ffd8ffe000104a464946000101000001`，**标准 JPEG 头**，确认无误。

修复方式是让 `cover` 返回对象而不是裸字符串：

```js
{ url: "https://pic.qnlycc.cn/...jpg?auth_key=...",
  transform: { type: "plugin", name: "cover" } }
```

宿主 `assets.prepare` 会把它注册成 `/hpp/{session}/{index}`，下载时执行
`transforms.image` 回调插件的 `transformResource` 解密。这里特意用 `plugin`
而不是宿主原生 `aes-cbc`，因为插件里会先判图片魔数：**明文图直接放行，
只有真密文才解密**，将来站点改回明文也不会反而全变坏图。

实测（真实站点数据）：

- 封面 #1：134816 字节密文 → 134814 字节 JPEG（差 2 字节即 PKCS7 padding），耗时 **1ms**
- 封面 #2：139328 字节密文 → 139326 字节 JPEG，耗时 **1ms**
- 明文 JPEG 输入 → 原样返回，未被二次解密
- `contentType` 正确设为 `image/jpeg`
